<GOAL>
  You are an expert technical editor and QA specialist. Your task is to "deslop" a deep insights report: 
  remove redundancy, ensure every insight is high-quality and actionable, merge duplicates, and fix formatting.
  
  Input: A markdown report with analysis findings, suggested fixes, and contributor annotations.
  Output: A clean, concise, high-impact version of the report ready for engineering leadership.
</GOAL>

<INPUT_FILE>
  /tmp/analysis_findings.md
</INPUT_FILE>

<OUTPUT_FILE>
  /tmp/analysis_findings.md
</OUTPUT_FILE>

<QUALITY_GATES>
  Apply these rules to every insight. If an insight fails a critical gate, DROP IT entirely.

  1. **Relevance Gate**:
     - DROP if the insight is marked ONGOING but "Last seen" is > 24 hours ago (unless explicitly noted as a regression that started >24h ago but is still active).
     - DROP if the "Impact" is trivial (e.g., < 5% change in latency for a non-critical endpoint, or < 10 errors total per day).
     - DROP if the "Evidence" section shows the pattern existed in the baseline week at similar levels (it's noise).
     - DROP if the root cause is explicitly identified as "external" or "upstream" with no actionable fix on our side.

  2. **Completeness Gate**:
     - DROP ONGOING insights that are missing a "Suggested Fix" section.
     - DROP insights missing "Code Location" or "Evidence" (queries/errors).
     - DROP insights where "Affected Accounts" contains only session IDs or "unknown".

  3. **Deduplication Gate**:
     - MERGE insights that share the same root cause (e.g., "Error spike on X" and "Latency spike on X" due to same DB query). Combine them into one insight listing both impacts.
     - MERGE insights for the same endpoint.
     - DEDUPLICATE the "Functions Involved" list if the same function appears multiple times.

  4. **Actionability Gate**:
     - ENSURE every ONGOING insight has a concrete, specific "Suggested Fix". If the fix is vague ("optimize query"), flag it or drop if not useful.
     - RECLASSIFY to RESOLVED (or DROP) any ONGOING insight whose "Suggested Fix" concludes there is no code change needed (e.g., "no fix required", "natural variation", "expected behavior", "not a bug"). If the insight has informational value, move it to the Resolved Events section. If not, drop it entirely.
</QUALITY_GATES>

<EDITING_RULES>
  1. **Structure & Placement**:
     - **Suggested Fix**: Must ONLY contain the fix and explanation. Move any metrics/context to "What Happened".
     - **What Happened**: Must contain the metrics, delta, and impact. Move any timeline details to "Timeline".
     - **Root Cause**: Must be a 1-2 sentence technical summary. Remove repetition of metrics.
     - **Code Location**: Must contain actual code snippets. Move SQL queries to "Evidence".

  2. **Text Quality (Deslop)**:
     - REMOVE filler phrases: "It is worth noting", "As seen in the data", "This indicates that", "We observed", "Importantly".
     - REMOVE redundant restatements.
     - CONCISE prose: "Latency increased 50ms -> 500ms" is better than "We observed a significant increase in latency from 50ms to 500ms".
     - PRESERVE `<@U...>` Slack mentions in the "**Contributors:**" line. This is critical.

  3. **Formatting**:
     - TIME: Convert all durations to human-readable (e.g., "150ms", "2.5s", "5m"). No raw nanoseconds.
     - LINKS: Ensure all HUD links use `app.hud.io` domain.
     - LINKS: Ensure endpoint links are `.../endpoints/{endpoint_id}-{service_id}...`.
     - CODE BLOCKS: Ensure correct language tags (ts, sql, json).

  4. **Ranking & Limits**:
     - RE-RANK insights by Impact (Magnitude * Volume).
     - KEEP MAX 5 ONGOING insights. Drop the rest (or list as one-line "Honorable Mentions" at the end if they are valid but lower priority).
     - KEEP MAX 3 RESOLVED events.
</EDITING_RULES>
